# Database Layer — Prisma + PostgreSQL

This folder contains the full database layer for the Multi-Vendor Food Delivery Platform: schema definition, migrations, seed data, and CRUD operations, implemented with Prisma against PostgreSQL.

## Contents

| File | Purpose |
|---|---|
| `schema.prisma` | Data model — 9 models, enums, and relationships |
| `migrations/` | Version-controlled SQL migrations generated by Prisma |
| `seed.js` | Populates all 9 tables with realistic sample data, in dependency order |
| `crud.js` | Example Create, Read, Update, and Delete operations against the schema |

## Schema Overview

### Entities

| Entity | Description |
|---|---|
| `Restaurant` | A vendor on the platform — name, description, cuisine type, open/closed status, address |
| `Category` | Platform-wide menu categories (e.g. Main Course, Beverages) |
| `MenuItem` | An item offered by a restaurant, belonging to one category |
| `Customer` | A platform user — name, unique email |
| `Address` | A saved delivery address, owned by one customer |
| `Rider` | Delivery personnel — name, phone, availability |
| `Order` | Placed by a customer at one restaurant, optionally assigned a rider, tracked by status |
| `OrderItem` | Junction table linking an `Order` to the `MenuItem`s it contains, with quantity and price snapshot |
| `Review` | Feedback on an order, targeting either the restaurant or the rider |

### Relationships

- Restaurant → MenuItem: one-to-many
- Category → MenuItem: one-to-many
- Customer → Address: one-to-many
- Customer → Order: one-to-many
- Restaurant → Order: one-to-many
- Rider → Order: one-to-many (optional — an order may have no rider assigned yet)
- Order ↔ MenuItem: many-to-many, resolved via the `OrderItem` junction table
- Order → Review: one-to-many

### Enums

- `OrderStatus`: `PLACED`, `PREPARING`, `OUT_FOR_DELIVERY`, `DELIVERED`, `CANCELLED`
- `TargetType`: `RESTAURANT`, `RIDER` — identifies what a given `Review` row is for

## Non-Obvious Design Decisions

**Categories are platform-wide, not restaurant-specific.**
A single `Category` table is shared across all restaurants (e.g. "Main Course" applies platform-wide), rather than each restaurant defining its own categories. This keeps categorization consistent for cross-restaurant browsing and filtering.

**Reviews use a `targetType` field rather than separate rating columns.**
Since a review may be for the restaurant, the rider, or both, each review targets exactly one of the two via a `targetType` enum, with a single `rating` and `comment` field. An order can therefore have zero, one, or two review rows. This was chosen over a single row with nullable `restaurantRating`/`riderRating` columns, since it keeps every row uniform in meaning and avoids unused columns.

**`OrderItem` stores a `priceAtOrder` snapshot, separate from `MenuItem.price`.**
Restaurants can change menu prices after an order has already been placed. Storing the price at the time of the order preserves accurate historical order totals, independent of later price changes.

**Customer ↔ Address is one-to-many, not many-to-many.**
Although two people could physically share a residential address, the schema models *saved address records* per customer account — matching how a real delivery app's "saved addresses" feature works — rather than a shared address entity. The design reflects what the application needs, not just what is physically possible.

**Restaurant stores a plain `address` field, not a relation to `Address`.**
A restaurant has exactly one fixed business location, unlike a customer who may save multiple delivery addresses. A relation table is unnecessary overhead for a single fixed value.

**Delete is implemented selectively, not uniformly.**
`Address` supports deletion (`deleteAddress`), since saved addresses are low-stakes, disposable data. `Order` does not support deletion — an order is historical business data, and its lifecycle is represented by moving through `OrderStatus` (including `CANCELLED`) rather than being removed.

## Setup

```bash
# From the project root
npm install

# .env should contain:
# DATABASE_URL="postgresql://USER:PASSWORD@HOST:PORT/DATABASE_NAME?schema=public"

npx prisma migrate dev
npx prisma generate
node prisma/seed.js
```

## CRUD Operations (`crud.js`)

| Function | Operation | Description |
|---|---|---|
| `placeOrder` | Create | Creates an `Order` and its `OrderItem` rows together inside a `$transaction`, guaranteeing atomicity |
| `addReview` | Create | Adds a review for an order, targeting the restaurant or rider |
| `getCustomerOrders` | Read | Fetches a customer's orders with related restaurant, items, and rider data via `include` |
| `getRestaurantMenu` | Read | Fetches a restaurant's available menu items with category data via `include` |
| `assignRider` | Update | Assigns a rider to an existing order |
| `updateOrderStatus` | Update | Updates an order's status |
| `deleteAddress` | Delete | Removes a customer's saved address |

## ERD

The ERD (`../ERD.svg`) is generated directly from `schema.prisma` via `prisma-erd-generator`, so it is always guaranteed to be in sync with the actual implemented schema:

```prisma
generator erd {
  provider = "prisma-erd-generator"
  output   = "../ERD.svg"
}
```

Regenerate at any time with:

```bash
npx prisma generate
```
